# 오픈 체크리스트

> **실제 매장 데이터가 준비됐을 때** 프로토타입 더미 데이터를 걷어내고 오픈하기
> 위해 확인할 목록. 지금 저장소에 들어 있는 맥주 7종 · 사진 · 매칭율은 전부
> [`docs/prototype.html`](./prototype.html) 에서 온 **더미 값**이다.
>
> - 맥주 데이터: [`src/data/beers.ts`](../src/data/beers.ts) · 스키마 [`docs/beer-schema.md`](./beer-schema.md)
> - 질문 데이터: [`src/data/questions.ts`](../src/data/questions.ts) · 가이드 [`docs/question-guide.md`](./question-guide.md)
> - 가중치 표: [`docs/scoring-map.md`](./scoring-map.md)
> - 배포 설정: [`README.md`](../README.md#배포)

각 항목의 상태는 오픈 담당자가 채운다. **결정이 필요한 항목(4 · 5)은 코드보다
정책이 먼저다** — 정하지 않으면 구현할 수 없다.

## 1. 맥주 사진 라이선스 확인

현재 7종 전부 **Pexels 원격 이미지**이고, 매장 맥주 사진이 아니라 분위기만 맞는
스톡 사진이다. URL은 `src/data/beers.ts` 의 `photo` 필드에 직접 박혀 있다.

| 맥주 | Pexels photo ID |
|---|---|
| 골든 라거 | 5538223 |
| 트로피컬 IPA | 13027856 |
| 바나나 클로브 바이젠 | 5538222 |
| 레몬 고제 | 5538225 |
| 카카오 스타우트 | 5659493 |
| 오크 배럴 스트롱 에일 | 5659756 |
| 디저트 페이스트리 스타우트 | 5538224 |

- [ ] **원칙: 실제 판매 맥주를 직접 촬영한 사진으로 교체한다.** 스톡 사진은
      "이 맥주가 이렇게 나온다"는 잘못된 기대를 만든다.
- [ ] 촬영 사진으로 교체할 경우 세로 비율(결과 카드는 세로로 긴 영역)로 준비한다.
- [ ] 스톡 사진을 계속 쓴다면 Pexels 라이선스 조건(상업적 사용 가능 · 출처 표기
      의무 없음)이 **현재도 유효한지 사진별로 재확인**한다. 라이선스는 업로더가
      바꿀 수 있고, 사진이 내려가면 링크가 죽는다.
- [ ] 사진에 사람 얼굴 · 타 브랜드 로고가 찍혀 있지 않은지 확인한다.
- [ ] **외부 URL 직참조를 계속할지 결정한다.** 지금은 Pexels가 죽으면 사진이
      깨진다. 매장 사진으로 바꾼다면 `public/` 에 두고 로컬 경로를 쓰는 편이
      안전하고 빠르다.
- [ ] 사진 호스트를 바꿨다면 [`next.config.ts`](../next.config.ts) 의
      `images.remotePatterns` 도 같이 고친다 — **안 고치면 이미지가 차단된다.**
      (`public/` 로컬 파일로 옮겼다면 이 설정 자체가 필요 없어진다.)

> 사진이 깨져도 화면은 죽지 않는다 — [`BeerPhoto`](../src/components/screens/result/BeerPhoto.tsx)
> 가 회색 배경 + 맥주 이모지로 대체한다. **조용히 대체되므로 오픈 전에 7종
> 전부 눈으로 확인한다.**

## 2. 실제 판매 중인 메뉴와 일치하는지

지금 7종은 스타일 카테고리마다 딱 1종씩 있는 인공적인 구성이다. 실제 매장
탭리스트는 이렇게 고르게 분포하지 않는다.

- [ ] 7종의 **이름 · `abv` · `ibu` · `pairing`** 이 실제 메뉴판과 일치하는지 확인
      (현재 값은 프로토타입에서 온 더미다).
- [ ] **판매하지 않는 맥주를 추천하지 않는지** 확인 — 손님에게 없는 걸 권하는
      것이 이 앱의 최악의 실패다.
- [ ] 시즌 메뉴 · 품절을 어떻게 다룰지 정한다. 지금은 재고 개념이 없어서
      `BEERS` 에 있으면 무조건 추천 후보다. 품절을 반영하려면 필드
      (예: `available: boolean`)를 추가하고 `recommend()` 에서 걸러야 한다.
- [ ] 스타일당 맥주가 2종 이상으로 늘어나면 `id` 와 `styleId` 를 분리한다
      (예: `id: "summer-lager"` / `styleId: "clean-lager"`). 구조는 이미
      배열이라 버티고, 같은 스타일 안에서는 Q1 · Q2 신호가 순위를 가른다.
      자세한 규칙은 [`docs/beer-schema.md`](./beer-schema.md).
- [ ] 스타일 카테고리 자체가 매장 메뉴와 안 맞으면 Q4(`style`) 선택지부터
      고친다. **선택지 `id` 와 `styleId` 는 같은 값이어야 한다.**
- [ ] 맥주를 추가 · 삭제한 뒤 `npm run check:questions` 를 돌린다.

## 3. `profile` 스코어 재검토

`profile` 은 프로토타입에 없던 **추천 전용 필드**로, 각 맥주의 `taste` · `tags`
문구를 근거로 개발 중에 추정해 매긴 값이다. 화면에 보이지 않으므로 틀려도
드러나지 않고, 추천 품질에만 조용히 영향을 준다.

현재 값 (각 축 0~5):

| 맥주 | sweetness | bitterness | aroma | body | refreshing |
|---|---|---|---|---|---|
| 골든 라거 | 2 | 1 | 2 | 1 | 5 |
| 트로피컬 IPA | 2 | 4 | 5 | 3 | 3 |
| 바나나 클로브 바이젠 | 3 | 1 | 4 | 3 | 3 |
| 레몬 고제 | 3 | 1 | 3 | 1 | 5 |
| 카카오 스타우트 | 3 | 3 | 4 | 5 | 1 |
| 오크 배럴 스트롱 에일 | 3 | 2 | 5 | 5 | 0 |
| 디저트 페이스트리 스타우트 | 5 | 2 | 4 | 4 | 0 |

- [ ] **맥주를 실제로 마셔 본 사람이 값을 다시 매긴다.** 사장님 · 브루어처럼
      맛을 아는 사람의 감각이 개발자의 추정보다 정확하다.
- [ ] 축의 의미를 합의한 뒤 매긴다 — 특히 `body`(바디감)와 `aroma`(향의 세기)는
      사람마다 해석이 갈린다. 기준은 [`docs/scoring-map.md`](./scoring-map.md).
- [ ] `ibu` 와 `bitterness` 가 서로 모순되지 않는지 본다 (IBU 55인 IPA가
      `bitterness: 4` 인 것처럼 방향이 맞아야 한다).
- [ ] 값을 바꾼 뒤 `npm run check:questions` 로 각 스타일 선택지가 여전히 자기
      스타일 맥주를 1순위로 뽑는지 확인한다.
- [ ] 손으로도 몇 번 돌려 본다 — 특히 **Q1 · Q2가 결과를 뒤집지 않는지**.
      스타일 경계는 `STYLE_BONUS` 가 지키게 되어 있지만, 스타일당 여러 종이
      되면 Q1 · Q2가 실제로 순위를 가르기 시작한다.

## 4. 매칭율(`match`) 값 정책 결정 — **결정 필요**

결과 화면의 `매칭 95%` 는 **계산값이 아니라 `beers.ts` 에 박아 둔 상수다.**
프로토타입이 그랬기 때문에 재현한 것이고, 지금은 누가 어떻게 답해도 그 맥주가
나오면 항상 같은 숫자가 뜬다.

현재 하드코딩 값: 라거 95 · IPA 93 · 바이젠 92 · 고제 91 · 스타우트 96 ·
스트롱 에일 90 · 디저트 스타우트 94.

두 갈래 중 하나를 고른다.

**(A) 하드코딩 유지**

- 장점: 프로토타입 · 피그마와 100% 일치. 항상 90%대 초반 이상이라 손님이 보기에
      기분이 좋고, 숫자가 낮게 나올 위험이 없다.
- 단점: **사실상 장식이다.** 답변과 무관하므로 "매칭"이라는 말이 정직하지 않고,
      같은 맥주를 두 번 추천받으면 숫자가 똑같아서 눈치채는 손님이 있다.

**(B) 계산값 표시**

- 계산은 이미 있다. [`recommend()`](../src/lib/recommend.ts) 가 후보마다
      `score`(0~100 유사도)를 이미 들고 있고, `matchPercent: beer.match` 를
      `matchPercent: Math.round(score)` 로 바꾸는 **한 줄이면 된다.**
- 단점: 값의 범위가 넓어진다. 유사도는 60~70%대도 흔히 나오는데, 손님에게
      `매칭 62%` 를 보여줄 것인지가 진짜 질문이다. 하한을 두거나(예: 최소 85%)
      구간을 재사상(remap)하면 결국 "정직한 계산값"도 아니게 된다.
- 피그마 디자인의 배지 폭이 두 자리 수 기준인지도 확인해야 한다.

- [ ] A / B 중 하나를 정한다. **정하기 전에는 코드를 건드리지 않는다.**
- [ ] B를 고르면 하한 · 반올림 규칙을 함께 정하고 `docs/scoring-map.md` 에 적는다.
- [ ] A를 유지하면 `match` 값이 맥주 추가 시 무엇을 기준으로 붙는 숫자인지
      `docs/beer-schema.md` 에 명시한다 (현재는 근거가 프로토타입뿐이다).
- [ ] 어느 쪽이든 **"매칭"이라는 라벨 문구를 바꿀지**는 디자인과 함께 결정한다
      (화면 문구는 임의로 고치지 않는다).

> `match` 는 대표 맥주를 고르는 데도 쓰인다 — `getBeerByStyle()` 이 같은 스타일
> 중 `match` 가 가장 높은 종을 대표로 뽑는다. 정책을 바꿀 때 이 쓰임도 같이 본다.

## 5. 별점 데이터 저장 필요 여부 → API 연동 검토 — **결정 필요**

결과 화면의 별점 시트는 지금 **아무 데도 저장하지 않는다.** 별을 누르면 감사
화면으로 넘어가고 값은 그대로 사라진다 (프로토타입도 그랬다).

받을 자리는 이미 열려 있다.

- [`src/types/feedback.ts`](../src/types/feedback.ts) 의 `RatingSubmission` —
  별점 · `beerId` · `styleId` · 그때의 답변 · 시각을 담는다.
- `RatingSubmitHandler` 를 `<BeerFinderApp onSubmitRating={…} />` 로 주입하면
  된다. 지금은 아무도 넘기지 않아서 화면 동작에 영향이 없다.

- [ ] **별점을 실제로 쓸 것인지 먼저 정한다.** 안 쓸 데이터를 모으는 것은
      개인정보 · 운영 비용만 늘린다. 쓸 거라면 무엇을 보고 싶은지 —
      "어떤 맥주가 만족도가 낮은지" 인지, "어떤 답변 조합이 빗나가는지" 인지.
- [ ] 저장한다면 저장소를 정한다 (Vercel Postgres · KV · 외부 시트 · 분석 도구 등).
- [ ] 개인정보를 담지 않는지 확인한다. 현재 `RatingSubmission` 에는 식별자가
      없고 답변 맥락만 있다 — **이 성질을 유지한다.** IP · 기기 식별자를 함께
      저장하기 시작하면 성격이 달라진다.
- [ ] 매장 태블릿은 손님이 돌려 쓰는 공용 기기라는 점을 감안한다. 중복 · 장난
      입력을 어떻게 다룰지(rate limit · 세션당 1회) 정한다.
- [ ] 실패를 조용히 넘긴다. 별점 전송이 실패해도 **손님 화면은 절대 막히지
      않아야 한다** — 감사 화면은 그대로 뜨게 한다.

### ⚠️ 배포 방식에 영향을 준다

API를 붙이면 **정적 export(`output: 'export'`)를 쓸 수 없게 된다.** Route
Handler의 `POST` · Server Action · 요청 기반 로직은 정적 export가 지원하지
않는다. Vercel처럼 서버가 있는 호스팅이 필요하다.

- [ ] 정적 호스팅을 계속 쓸 계획이었다면 이 시점에 배포 방식을 다시 정한다.
      (서버 없이 가려면 외부 SaaS 엔드포인트로 클라이언트에서 직접 보내는
      방법이 있지만, 키가 브라우저에 노출되는 문제를 따져야 한다.)
- [ ] 결정한 내용을 [`README.md`](../README.md#배포) 의 배포 절에 반영한다.
